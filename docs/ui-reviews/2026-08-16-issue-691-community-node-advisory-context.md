## 確認した流れ

1. 著者詳細でコミュニティノードを選び、信頼評価、関係分析、近傍一覧を読み込む。
2. 読み込み開始時の対象利用者、選択ノード、要求世代を三つの結果と一体で保持する。
3. 対象利用者または選択ノードが変わると、以前の結果、エラー、読込中状態、異議申し立て対象を消す。
4. 遅れて完了した古い要求は表示へ反映せず、現在の対象とノードに対する最新要求だけを表示する。
5. リスク判定の根拠から異議申し立てを開き、送信時にも対象利用者、選択ノード、要求世代の一致を確認する。
6. 送信後は受付結果を表示したまま現在の文脈で情報を再取得し、申立て中の状態へ更新する。

## 画面設計の確認

- 一貫性: 既存の著者詳細、信頼・関係画面、通知、異議申し立て画面の部品と用語をそのまま使う。
- 操作の近道: 根拠から直接異議申し立てを開ける既存の操作数を増やさない。
- 状態の明示: 読込中、取得結果、既知の失敗、申立て中、解消済みを既存の表示で区別する。
- 操作完了: 異議申し立て受付後は受付結果と受付番号を表示し、その後の再取得で申立て中の状態を示す。
- 誤操作の防止: 対象利用者またはノードが変わった時点で古い根拠を失効させ、古い応答と送信操作を受け付けない。
- 取り消しやすさ: 送信前は異議申し立て画面を閉じて著者詳細へ戻れる。
- 利用者の主導権: ノード選択、情報取得、異議申し立て送信は利用者の明示操作でのみ行う。
- 記憶負担の軽減: 取得時の対象とノードを内部で保持するため、利用者が情報の取得元を覚えて照合する必要がない。

## 検証

- `CommunityNodeAdvisoryPanel` の部品試験で、対象利用者切替、ノード切替、読込中の切替、応答順逆転、異議申し立て画面の失効、送信後の再取得を確認
- 部品見本で、著者詳細内の信頼評価、関係分析、近傍一覧、リスク判定根拠を確認
- `community_node_trust_relation_client` で信頼評価、関係分析、近傍一覧、距離による利用停止、安定したエラーの通信経路を確認
- `cargo xtask desktop-ui-check` と `cargo xtask check` は成功
- `cargo xtask test` は変更対象外のリレー同期試験2件が90秒で期限切れになった。2件を除いた残り570件は再実行で全件成功し、期限切れ2件は個別再実行でも同じ結果だった
